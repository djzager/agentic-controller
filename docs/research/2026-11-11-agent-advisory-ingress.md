# Concrete vulnerability ingress for an AgentSession spike

Research date: 2026-11-11. Primary documentation and limited read-only Hub inspection; no external subscriptions, alerts, or resources were created. Proposed boundaries and field names below are alternatives, not a settled CRD schema.

## Recommendation

Use **one GitHub repository with existing Dependabot alerts and an explicit Hub application/session mapping** for the first spike. A small adapter can poll the repository alerts API, persist observed findings and pending fanout, then create deterministic AgentInputs for the mapped sessions. This needs no public webhook endpoint. Add `dependabot_alert` webhooks as a lower-latency path into the same durable inbox; retain polling for reconciliation. This tests waking, fanout, restart, and deduplication without first building a global vulnerability matcher.

If GitHub integration is unsuitable, the provider-neutral alternative is **OSV batch queries over a small, explicitly versioned dependency snapshot** for two applications. Querying inventory periodically is simpler than initially consuming every global advisory and implementing all ecosystem version-range matching. An authentic result can be recorded and replayed to exercise crash boundaries without modifying a production repository.

## What each upstream source actually provides

**GitHub repository alerts.** Dependabot evaluates supported dependency graphs on the default branch when advisories or dependencies change. An alert identifies a repository finding, affected file, vulnerability, and sometimes a fixed version. It is not proof that deployed code is exploitable, and it does not cover arbitrary application branches or all vulnerabilities. The repository REST endpoint supports read-only GitHub App access, pagination, and sorting by alert creation or state-update time; `updated` is not an advisory change-stream cursor. [Dependabot behavior](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts), [alerts REST API](https://docs.github.com/en/rest/dependabot/alerts)

**GitHub notification choices.** `dependabot_alert` is available to repository/organization webhooks and GitHub Apps; Apps require read access to Dependabot alerts. In contrast, `security_advisory` is a GitHub-App-only event about a GitHub-reviewed global advisory, not an affected-application notification. The older `repository_vulnerability_alert` event is closing down. Webhooks include a delivery identifier and support an HMAC signature. GitHub does not automatically retry failed webhook deliveries. A receiver therefore needs durable acceptance and a recovery path, such as scheduled reconciliation or scripted redelivery. [Webhook event reference](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [failed delivery behavior](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)

**OSV inventory lookup and advisory deltas.** `POST /v1/querybatch` accepts package/version, versioned PURL, or Git commit queries and returns matching vulnerability IDs and modification timestamps; pagination is per query. Full records are available separately. OSV also exports `modified_id.csv` globally and per ecosystem, ordered newest first, plus individual JSON records and full archives. These provide a concrete polling source for later global-advisory fanout. They do not identify the organization's applications: the adapter/Hub must connect exact dependency coordinates and inventory revisions to applications. [Querybatch](https://google.github.io/osv.dev/post-v1-querybatch/), [data exports and deltas](https://google.github.io/osv.dev/data/)

**NVD.** NIST explicitly documents synchronization using `lastModStartDate`/`lastModEndDate`, and currently provides 2.0 feeds/APIs. Its 2026 changes demonstrate why consumers must process revisions: large data corrections can update many records, and some CVEs will not receive immediate enrichment. Use bounded modified-time windows, pagination, replay overlap, and durable checkpoints for an NVD adapter; publication-only polling misses later corrections. The current developer page returned no readable body in this research environment. The commonly documented 120-day window maximum was not independently revalidated against that live primary page and should be checked before implementing this adapter. [NIST operational and API updates](https://www.nist.gov/itl/nvd), [developer reference to verify](https://nvd.nist.gov/developers/vulnerabilities)

**Red Hat.** Public sources include CSAF security advisories, per-CVE VEX covering fixed/unfixed product components, and an RHSA RSS feed containing only the last three days of advisories. Red Hat also exports RPM advisory data into OSV and directs consumers to OSV. RSS alone cannot recover an outage longer than its retained window; a durable adapter needs archive/API catch-up. Product-specific VEX is relevant when mapping Red Hat builds, rather than treating an upstream package/version match as sufficient. [Red Hat security data and feed links](https://access.redhat.com/security/data)

## Ownership and inventory evidence

The generic controller receives AgentInputs and reconciles execution. A source adapter authenticates upstream deliveries, normalizes findings, and persists receipt/checkpoint state. **Hub or an inventory-aware integration resolves affected applications and chooses their sessions.** Global advisory announcement, package-version match, affected repository, and confirmed deployed applicability are different evidence levels; record which level justified routing.

The inspected Hub API already has application repository URL/branch/tag/path, analysis application/commit, and technical dependencies with provider/name/version/indirect/SHA. The inspected dependency shape has no explicit PURL or ecosystem field, so OSV normalization and inventory freshness cannot be assumed complete. Hub `/dependencies` is application-to-application dependency edges, not this software package inventory. Inspection was limited to API shapes, not a full audit of every analyzer or external integration. Local inspected sources: [application](https://github.com/konveyor/tackle2-hub/blob/3fecffe813437d3ea66d0a33eafa32fe3091f582/shared/api/application.go#L9), [repository shape](https://github.com/konveyor/tackle2-hub/blob/3fecffe813437d3ea66d0a33eafa32fe3091f582/shared/api/core.go#L120), [analysis and technical dependencies](https://github.com/konveyor/tackle2-hub/blob/3fecffe813437d3ea66d0a33eafa32fe3091f582/shared/api/analysis.go#L16).

## Smallest durable end-to-end flow

1. Configure one repository and explicit target sessions. For the spike, avoid inferred URL equality across hosts and ambiguous monorepo ownership; resolve a stable repository ID and manifest path to a reviewed application mapping.
2. Read all pages of current alerts on initial sync and periodically thereafter. Persist findings with provider/host/repository ID/alert number, relevant source revision or normalized content digest, and current state. Keep advisory IDs and CVE aliases separately: not every advisory has a CVE, and one advisory can have several application/package findings.
3. Durably record the routing decision, inventory/mapping revision, and pending delivery for each chosen session. Create each AgentInput with a stable key derived from finding revision plus target session UID. Retrying after a crash must discover the same input, not create another.
4. Advance a polling checkpoint only after observations and fanout obligations are durable. The adapter need not wait for agent completion. For a tiny repository, full periodic reconciliation is easier to reason about than treating a mutable REST pagination cursor as a permanent event offset.
5. For webhooks, validate the signature and persist the receipt before returning success. Deduplicate transport deliveries by delivery ID and semantic findings by finding/revision identity; webhook and poll observations can refer to the same work. A stale webhook must not overwrite newer reconciled state.
6. A single finding can fan out to several applications/sessions, but partial fanout must remain retryable. A changed advisory, resolved alert, or newly changed inventory is a new observation whose routing policy may differ; do not silently treat every modification as another remediation request.

For OSV delta ingestion, persist `(modified timestamp, record ID/path)` identity, process the complete timestamp boundary, and replay an overlap. Save changed records before advancing the watermark. Periodically re-query inventory because applications can acquire an already-known vulnerable version without any new advisory publication. Do not claim the CSV is an ordered, append-only message log.

## Configuration alternatives to discuss

- **Separate source and routing configuration:** source kind, endpoint/host, credential or webhook-secret reference, polling interval, initial-sync policy, recovery lookback; routing application/manifest scope, eligible session selector, normalized event types, optional severity/state filters, and input template. Cursor, receipts, and delivery progress belong in durable observed state, not user-authored desired state.
- **Session-local subscription:** AgentSession references an external normalized source and declares relevant event types/labels. Hub still computes applicability and stamps generic routing metadata. This is convenient for ownership but should not make the controller understand CVE package ranges or Hub inventory.
- **PoC-only configuration:** a file/ConfigMap plus a durable database or receipt CR is sufficient to test the protocol. This tests the delivery protocol but does not satisfy the requested proof of a CR-configured notification path; that demonstration still needs concrete source/binding resources.

Acceptance scenarios: one real finding wakes one session; one finding reaches two intended sessions; duplicate webhook plus poll creates no duplicate work; process dies after one fanout child and completes the rest on restart; previously unseen open alerts are found after ingress downtime; changed inventory is re-evaluated; ambiguous applicability is visible rather than silently routed everywhere.
