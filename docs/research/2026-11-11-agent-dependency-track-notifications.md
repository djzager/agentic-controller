# Dependency-Track as an SBOM finding notification source

Research date: 2026-11-11. Research only; no product, architecture, or public API decision. No deployments, credentials, or external registrations were made.

## Finding and version boundary

Dependency-Track is a concrete candidate for the SBOM → affected project finding → notification part of the proposed agent loop. Its current homepage advertises 5.2, and the 5.2 release announcement explicitly includes signed webhooks. The findings below use official rolling `/docs/next/` documentation, which describes v5 and explicitly marks signing as available since 5.2. These are documentation findings, not a test of a pinned 5.2 image or source tag. Pin and verify before promising implementation guarantees. [Homepage](https://dependencytrack.org/), [5.2 announcement](https://dependencytrack.org/news/dependency-track-5-2/).

The older `docs.dependencytrack.org` notification documentation is labeled v4.14. Its payload examples and delivery implementation must not be presented as current v5 behavior. In particular, v4 `NEW_VULNERABILITY` examples contain multiple affected projects. [Legacy notifications](https://docs.dependencytrack.org/integrations/notifications/).

## What the current official docs establish

- **Events:** `NEW_VULNERABILITY` means a newly identified vulnerability; `NEW_VULNERABLE_DEPENDENCY` means a vulnerable component became a project's dependency. `PROJECT_AUDIT_CHANGE` covers analysis/suppression changes, and `VULNERABILITY_RETRACTED` covers withdrawn reports. These are event triggers; summary groups are scheduled. `BOM_PROCESSED` reports successful BOM processing, so do not treat it alone as proof that the desired finding notification was produced. [Notification groups](https://dependencytrack.github.io/docs/next/reference/notifications/groups/).
- **Current payload and identity:** `Notification.id` is a UUIDv7. `NewVulnerabilitySubject` contains one project, component, and vulnerability. Its deprecated `affected_projects` list contains only that same project; consumers must not expect all affected projects there. `NewVulnerableDependencySubject` contains one project, one component, and a vulnerability list. Component UUID/PURL and project UUID provide correlation fields. Internal notifications are Protobuf; publisher templates can change wire representation. Preserve the notification ID when selecting a format/template. [Notification schema](https://dependencytrack.github.io/docs/next/reference/notifications/schema/).
- **Selection:** Alerts select scope, group, level, projects/tags, and optionally a CEL expression over payload content. Project/tag restrictions precede CEL. CEL evaluation errors are explicitly **fail-open**, so these filters are not an authorization boundary for admitting work into another tenant/session. [Notification concepts](https://dependencytrack.github.io/docs/next/concepts/notifications/).
- **Authentication:** The webhook publisher supports optional authentication and signing configuration. Since 5.2, a managed signing secret produces `X-Webhook-Signature: sha256=<hex HMAC-SHA256>` over exact outgoing body bytes; verify before parsing with constant-time comparison. Destination access is governed by `dt.outbound.allowed-destinations`. The signature documents integrity/authenticity, not freshness or deduplication. [Publishers](https://dependencytrack.github.io/docs/next/reference/notifications/publishers/).
- **Durability:** v5 documentation describes PostgreSQL-backed work queues, durable processing across restart, exponential retry backoff, and a transactional notification outbox. It states an at-least-once delivery contract requiring duplicate-tolerant consumers. PostgreSQL availability remains operator responsibility. v5 also changes notification schemas and REST response/pagination behavior; migration is not a transparent reuse of v4 integration code. [Changes in v5](https://dependencytrack.github.io/docs/next/concepts/changes-in-v5/).
- **Important qualifications:** Notifications without a potentially matching enabled alert are dropped before outbox insertion. Relay removal and workflow scheduling are atomic. Matched rules publish independently and can retry independently. Non-retryable failures terminate that rule. The overall publishing workflow counts as successful if **any** rule succeeds, so workflow success does not prove our destination received its notification. [Notification design](https://dependencytrack.github.io/docs/next/concepts/architecture/design/notifications/).
- **Retention/retry limits:** The durable engine uses activity attempt limits; retry exhaustion and terminal errors are possible. A maintenance worker deletes terminal workflow runs, history, inbox, and task records according to `dt.dex-engine.maintenance.run-retention-ms`. This bounded investigation did not establish webhook-specific attempt counts, HTTP error classification, default retention, a supported dead-letter/replay API, or stability of the rendered ID across every retry path. These are pinned-version spike checks, not assumed guarantees. [Durable execution](https://dependencytrack.github.io/docs/next/concepts/architecture/design/durable-execution/).

## REST reconciliation and version compatibility

There is an official v5 REST v1 reference, but this bounded investigation did not validate a v5 findings endpoint/response against its served OpenAPI. Before implementation, inspect the chosen image's schema for project listing, paginated findings including suppression/analysis state, upload completion, and notification-rule management. [REST v1 reference](https://dependencytrack.github.io/docs/next/reference/api/v1/).

For comparison only: inspected 4.14.0 source exposes `GET /api/v1/finding/project/{uuid}` and the findings export path, requires `VIEW_VULNERABILITY`, and checks project access. That supports a reconciliation approach conceptually; it does not certify the v5 wire contract. A current-state findings query also cannot recreate every intermediate historical event. [Pinned 4.14 FindingResource](https://raw.githubusercontent.com/DependencyTrack/dependency-track/4.14.0/src/main/java/org/dependencytrack/resources/v1/FindingResource.java).

## Proposed proof, not a chosen architecture

1. Pin a Dependency-Track version, use a controlled CycloneDX fixture, upload it to two known project versions, and provision an alert before generating findings. Map provider project UUIDs to the application/release and intended session outside the domain-agnostic controller.
2. Send signed notifications to the selected event ingress, validate authenticity and mapping, durably record receipt, then admit one input per intended target. The existing event-bus choice remains independent of the SBOM service choice.
3. Use `(source instance, notification ID)` for transport deduplication. Separately define semantic work identity from project/version, component, vulnerability identity, target session, and meaningful assessment revision. One CVE alone is insufficient. Two notification groups can describe overlapping work; a changed assessment may legitimately need fresh work.
4. Demonstrate both paths: a known vulnerable dependency entering an SBOM, and a new finding affecting an already tracked project. Observe that each affected project's event reaches its intended session. Have the session choose investigation/delegation/no action and record why; choosing action is distinct from finding affected software.
5. Prove duplicate POST, lost acknowledgement, ingress restart, partial downstream fanout, and child completion handling. Retain admission records independently of AgentInput garbage collection. Query current findings on startup/periodically for gaps, and make terminal notification failures observable per destination. Include suppression/retraction updates so old work can be reconsidered.

**Assessment:** Dependency-Track offers existing project-aware finding notifications, making it a useful comparison to Trustify for this experiment. Its documented v5 durability is materially stronger than the legacy v4 publisher behavior. Selection should turn on required SBOM/advisory semantics, deployment cost, supported integration APIs, and a verified recovery path—not just the existence of a webhook setting. This note does not independently establish Trustify's behavior.
